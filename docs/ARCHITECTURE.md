# Architecture

VisionAI is being rebuilt around an explicit safety-first pipeline:

Input adapters -> bounded event bus -> recognition services -> intent orchestrator -> typed action plan -> policy and permission engine -> confirmation gate -> serialized action dispatcher -> platform capability adapter -> result event -> UI, TTS, and audit history.

Ambiguous LLM command suggestions may ask one validated clarification question
on the CLI or desktop surface, then retry mapping once after the human answers.

Phase 7's first slice (see `docs/DECISIONS/0007-phase7-routines-first-slice.md`)
adds named routines: an ordered list of already-reviewed command phrases,
saved and run via `--routine-save`/`--routine-run`/`--routine-list`/
`--routine-delete`. A routine may only contain Risk 0 (read-only) or Risk 1
(reversible) phrases, checked both at save time and again immediately before
each dispatch at run time, and each step still runs through the unmodified
`TextCommandPlanner`/`SerializedDispatcher` path `--text` uses -- a routine
carries no authority of its own.

## Components (Phase 0 foundation + Phase 1 safety + Phase 4 capabilities + first Phase 2 UI slice)

- `visionai.core.events`: typed contracts for inputs, transcripts, gestures, intents, action plans, confirmations, pending permission requests, permission decisions, audit events, and error events.
- `visionai.core.state`: explicit assistant state machine, including a dedicated `AWAITING_PERMISSION` state distinct from `AWAITING_CONFIRMATION` (Section 7 names only `AWAITING_CONFIRMATION`, but permission and confirmation are gated separately and in a specific order by `PolicyEngine`, so representing them as two states keeps the state machine an accurate record of what is actually being waited on). Safe under concurrent access from multiple recognition threads (voice, gesture): `transition()`/`cancel()`/`on_transition()` are serialized by a lock, with listener callbacks notified outside it so a listener cannot deadlock or block other threads.
- `visionai.core.event_bus`: bounded asynchronous queue with close semantics. Closing signals over a separate `asyncio.Event` rather than a sentinel value competing for queue space, so the signal cannot be lost even if the queue is full; consumers still drain any already-queued events before observing closure.
- `visionai.core.cancellation`: cooperative cancellation token wrapping `threading.Event`.
- `visionai.core.cancellation.OperationController`: tracks the current cancellable operation for the early runtime so `system.stop` can request cancellation without killing threads.
- `visionai.config.settings`: environment-backed settings with conservative defaults.
- `visionai.config.user_settings.UserSettingsStore`: user-editable log level, microphone-device selection, and wake word, plus the onboarding-seen flag, in a small JSON file with the same atomic-write pattern as `JsonPermissionStore`. `effective_log_level()` returns the stored override if present, else `Settings.log_level`; `effective_wake_word()` mirrors that for the wake word, falling back to `DEFAULT_WAKE_WORD` ("visionai"). `set_wake_word()` collapses whitespace, lowercases, and rejects an empty or control-character value before writing. Both `visionai.app.main()` and `visionai.ui.main_window.main()` call `configure_logging(effective_log_level(...))` at startup so an edited level actually takes effect on the next run, not just live in the current process.
- `visionai.observability.logging`: redacted structured logging. The redaction filter is attached to every configured handler (not the root logger, whose own filters do not gate records from named child loggers) and redacts the fully substituted message so secrets passed as lazy `%`-style arguments are still caught.
- `visionai.observability.audit`: in-memory and JSON Lines audit sinks used by tests and early UI integration. Both reject an entire malformed log/entry rather than silently using a partial view, consistent with the permission store.
- `visionai.capabilities`: reviewed capability manifests and registry. Prohibited capabilities cannot be registered.
- `visionai.capabilities.system_info`: read-only capabilities -- `system.time`, `system.date`, `system.battery`, `system.health` -- with battery/CPU/memory probes backed by `psutil` and injectable for testing.
- `visionai.capabilities.meta`: registry/help/control surface -- `system.capabilities`, `system.help`, and `system.stop` for the initial safe Section 13 commands, plus `system.clear_history`, the first built-in Risk 2 capability. `system.clear_history` clears local audit history only after both a permission grant and a fresh confirmation; the dispatcher's own post-execution audit entry remains after clearing, so the clear operation itself is still visible.
- `visionai.capabilities.applications`: `app.open`, the first migrated behavior with a real side effect. Opens one allowlisted desktop application by exact executable name with `shell=False`; the allowlist deliberately excludes any general-purpose command surface (shell, terminal, task manager). See `docs/MIGRATION_QUARANTINE.md`.
- `visionai.capabilities.browser`: reversible browser capabilities -- `browser.open` and `browser.search` -- built from fixed site/search allowlists and `UrlPolicy` normalization before any browser opener is called.
- `visionai.capabilities.media`: `media.control`, a reversible allowlisted media-key capability with an injectable key presser so tests never send real keyboard events.
- `visionai.capabilities.dispatcher`: serialized handler dispatch after policy approval, with audit output. Audit records for both denials and successes use the registered capability's manifest risk level, never the caller-supplied request field, so a request cannot understate its own severity in the audit trail. `CapabilityHandler` is `(request, cancellation: CancellationToken) -> ActionResult`; `dispatch()` takes an optional `cancellation` keyword (defaulting to a fresh, never-cancelled token, so callers with nothing to track -- the CLI's direct dispatch -- need no change) and checks it once, centrally, immediately before invoking the handler, skipping execution entirely if it is already cancelled. `EventOrchestrator._execute()` passes the same token `OperationController.begin_operation()` returns, so cancelling that tracked operation (`system.stop`, the Stop button) is visible to any handler that polls its token -- today's built-in handlers are all fast/synchronous and do not, but the mechanism is what approved next task 3's voice/gesture handlers will use.
- `visionai.policy`: deterministic policy, persistent permission storage, rate limiting (thread-safe), URL validation helpers (deny-by-default: an empty host allowlist denies every host, not just non-private ones), and confirmation checks before any dispatcher can execute a request.
- `visionai.platform`: platform adapter boundaries. `lock_state` provides a static test adapter and Windows lock-state wrapper; the Windows wrapper checks whether the interactive input desktop can be opened (fails while the workstation is locked or a secure desktop such as a UAC prompt is active), and any check failure or unreachable desktop is treated as locked. `camera` defines the `GestureCandidate` shape and `LandmarkAdapter` boundary that hands only one classified candidate per frame to recognition code; raw frames/landmarks stay behind the adapter. `microphone` (the optional `voice` extra -- `sounddevice`/`numpy`, see `requirements/voice.txt`) provides `list_input_devices()` for real device enumeration and `MicrophoneCapture`, which records real audio in memory between `start()`/`stop()` and hands back one `numpy` array; the real PortAudio backend is only imported inside the two functions that touch it, so importing `visionai.platform` itself never requires the extra to be installed, and `visionai.platform.__init__` deliberately does not re-export `microphone` for the same reason. Speech-to-text stays out of scope: callers inject their own transcriber, matching `InputAdapter.publish_voice_capture()`'s existing boundary. `webcam` (the optional `vision` extra -- `mediapipe`/`opencv-contrib-python`/`numpy`, see `requirements/vision.txt`) provides the first real `LandmarkAdapter`: `WebcamLandmarkAdapter` reads one OpenCV frame and classifies it with mediapipe's legacy `solutions.hands` API (pinned to `mediapipe==0.10.14` -- later releases drop that offline API from their Windows wheels in favor of a Tasks API needing a downloaded model file; see `docs/DECISIONS/0003-accepted-protobuf-cve.md` for the resulting accepted transitive `protobuf` CVE, unreachable from any code path this project runs). Classification itself is a pure function, `classify_finger_count()`, over a small decoupled `HandLandmark(x, y)` shape rather than mediapipe's own landmark type, so it is unit-testable with fixture coordinates and needs neither a camera nor mediapipe installed; it recognizes a fixed vocabulary of six gestures (`open_palm`, `closed_fist`, `thumbs_up`, `peace_sign`, `index_finger_up`, `two_fingers`) by counting extended fingers, reporting anything ambiguous as no gesture rather than guessing. Both frame capture and classification are injectable on `WebcamLandmarkAdapter`, matching `MicrophoneCapture`'s injectable `stream_factory`. Only one classified `GestureCandidate` per frame ever crosses the boundary; raw frames/landmarks never leave this module, and `visionai.platform.__init__` deliberately does not re-export `webcam`, mirroring `microphone`.
- `visionai.intelligence`: Phase 6's first slice -- an LLM provider boundary with zero execution authority, mirroring `visionai.platform.lock_state`'s Protocol/static-fallback/real-implementation shape. `provider.py` defines `LLMQuery`/`LLMReply` (each just one `SafeText` field, reusing `core.events`' existing validated type rather than inventing new validation), the `LLMProvider` Protocol (`respond(query) -> reply`, plain synchronous like `LandmarkAdapter.read_candidate()`), and `DeterministicFallbackProvider` -- the always-available, no-network, no-key default `Settings.llm_provider == "none"` resolves to, so the app never makes an outbound call unless explicitly configured. `anthropic_provider.py` (the optional `intelligence` extra -- `anthropic`, see `requirements/intelligence.txt`) provides the first real provider, `AnthropicProvider`, calling the Messages API with a fixed, code-owned system prompt that states plainly the assistant cannot take actions; `anthropic` is only imported inside the constructor that builds a real client, and the client itself is injectable, so `visionai.intelligence`/`visionai.runtime` import fine and the automated suite runs fully without the extra installed or any network access, mirroring `WebcamLandmarkAdapter`. Client failures are caught broadly at this true external-I/O boundary (matching `WindowsLockStateAdapter`'s precedent, not the orchestrator's narrower `VisionAIError`-only catch) and converted to `core.errors.ProviderError`. `visionai --ask "<question>"` is the only entry point: it runs before `build_runtime()` (mirroring `--list-microphones`) and never touches the orchestrator, dispatcher, or event buses -- an LLM reply is only ever printed, never parsed as a command, so nothing in this slice can invoke a capability. `memory.py` adds `ConversationMemory`, a small bounded (turn-count and character-budget limited), explicitly clearable question/answer history that lives entirely on the caller's side of the `LLMProvider` boundary -- `respond(query) -> reply` itself is untouched; `ConversationMemory.build_query_text()` just prefixes as much recent history as fits into one outgoing `LLMQuery.text` before the caller sends it. `MainWindow`'s Ask AI button owns one `ConversationMemory` per window session (never persisted to disk, cleared on a new "Clear Conversation" button click); the CLI's `--ask` deliberately stays stateless (a fresh process per invocation, matching `docs/DECISIONS/0004-llm-provider-choice.md`'s original reasoning) and does not use it. `local_provider.py` (the optional `local_llm` extra -- `gpt4all`, see `requirements/local_llm.txt`) provides the second real provider, `LocalLlamaProvider`, for `Settings.llm_provider == "local"`: it runs a user-supplied GGUF model file entirely offline, and is constructed with `allow_download=False` so a missing or misconfigured `VISIONAI_LOCAL_MODEL_PATH` fails loudly (`_build_llm_provider()` raises a clear `ValueError` before ever constructing it) rather than silently reaching the network to fetch a model. Like `anthropic_provider.py`, its client is injectable and its failures (including a reply `LLMReply`'s `SafeText` field rejects) are caught broadly and converted to `core.errors.ProviderError`; unlike `anthropic_provider.py` (`anthropic` is part of `requirements/dev.txt`), `gpt4all` is imported via `importlib.import_module()` rather than a static import, mirroring `webcam.py`'s pattern for the same reason -- it is not part of the standard dev/CI dependency set. See `docs/DECISIONS/0006-local-offline-llm-provider.md` for why `gpt4all` was chosen over `llama-cpp-python` (prebuilt Windows wheels vs. a source-only PyPI release needing a local compiler) and what remains genuinely unverified in this Linux, no-GPU/no-model sandbox. See `docs/DECISIONS/0004-llm-provider-choice.md` for the original provider/model/secrets choices and what remains deliberately deferred (clarification -- an LLM asking a follow-up question when a request is ambiguous, a genuine new-feature design decision not yet scoped).
- `visionai.config.secrets`: closes the OS-keychain gap `0004` deferred -- mirrors `platform.lock_state`'s Protocol/in-memory-double/real-implementation shape again. `SecretStore` (`get`/`set`/`delete`), `InMemorySecretStore` (a real dict-backed round-trip test double), and `KeyringSecretStore` (the real implementation, backed by Windows Credential Manager via the optional `intelligence` extra's `keyring` package, imported lazily inside each method exactly like `anthropic` is in `anthropic_provider.py`, so `visionai.config` stays importable without it). `get()` fails soft (a keychain read failure is indistinguishable from "no key configured," matching `WindowsLockStateAdapter`'s "any check failure -> safe default"); `set()`/`delete()` fail loud, raising `core.errors.ProviderError`'s sibling `core.errors.StorageError` (the same one `JsonlAuditSink`/`JsonPermissionStore`/`UserSettingsStore` already use for local-persistence failures) rather than silently letting a user believe an unsaved key was saved. `resolve_anthropic_api_key(settings, store=None)` is the one function both `app._build_llm_provider()` and `main_window._build_llm_provider()` now call: the explicit `VISIONAI_ANTHROPIC_API_KEY` env var still wins if set (unchanged behavior), falling back to the keychain only when it's unset. `visionai --set-api-key` (prompts via `getpass.getpass()`, hidden input) and `visionai --delete-api-key` are the only new entry points, both running before `build_runtime()` like `--ask`/`--list-microphones` since neither needs the capability registry. See `docs/DECISIONS/0005-os-keychain-secret-storage.md`.
- `visionai.config.routines`: `RoutineStore`, mirroring `UserSettingsStore`'s atomic-write JSON pattern, persisting named ordered lists of command phrases. The store has no opinion on which phrases are safe -- that check (every phrase must plan to a Risk 0/1 capability) lives in `app.py`, which has the real planner the store deliberately does not depend on. See `docs/DECISIONS/0007-phase7-routines-first-slice.md`.
- `visionai.intelligence.planner.suggest_command()`: Phase 6's second slice -- the "structured planner" half of Section 12. It maps free text onto one of `TextCommandPlanner`'s own reviewed phrases via the LLM, but never itself builds an `ActionRequest` or touches the dispatcher -- that stays the caller's job. `visionai.orchestration.text_planner.reviewed_phrases()` enumerates every phrase/phrase-template `TextCommandPlanner.plan()` already accepts, built from the exact same dicts/allowlists `plan()` matches against (`_DIRECT_CAPABILITIES`, `_MEDIA_PHRASES`, `ALLOWED_APPLICATIONS`, `ALLOWED_SITES`, plus one `"search for <your query>"` template), so the LLM's menu can never drift out of sync with what's actually plannable. `suggest_command()` sends that menu plus the utterance to the configured `LLMProvider` and instructs it to reply with one exact phrase or the literal word `NONE` -- but never trusts that the reply followed instructions: it independently re-validates the raw text against the same reviewed vocabulary (case-insensitive exact match, or a `"search for "` prefix with real content after it) before returning anything at all. A hallucinated phrase outside that vocabulary -- including a prompt-injection attempt -- is indistinguishable from "no match" to every caller, satisfying Section 8's "reject unknown action names... never execute raw model output" by construction, not by a separate check. `visionai --suggest "<free text>"` is the only entry point: unlike `--ask`, it runs *after* `build_runtime()` (it needs the real registry-backed `TextCommandPlanner` to compute an accurate summary), calls `runtime.planner.plan(phrase)` on a validated result, and prints `"Proposed: <summary>"`. It then asks a genuine human confirmation question (`input("Execute this command? [y/N]: ")`, never anything derived from the LLM's own reply -- satisfying Section 12's "may not confirm itself"); only an explicit "y"/"yes" answer proceeds to `runtime.dispatcher.dispatch(plan.steps[0], runtime.policy_context_factory())`, the exact same unmodified call `--text` makes, so a capability still requiring its own permission grant or fresh confirmation (e.g. `system.clear_history`) is denied the same way `--text` already denies it -- this human question is an additional, LLM-provenance-specific gate layered in front of policy, not a replacement for it. Declining, or any non-"y" answer (including EOF/`Ctrl+C` on the prompt), prints `"Cancelled."` and dispatches nothing.
- `visionai.orchestration.TextCommandPlanner`: deterministic, non-LLM planning over already-captured text (Section 12's "deterministic parser"). Matches a small set of reviewed phrases and allowlisted slot values (app names, site names, media actions) and emits a typed `Intent` + `ActionPlan` -- never a raw dict, never an arbitrary capability. It is explicitly not the security boundary: an unrecognized or rejected slot produces an empty, non-executable plan, and any `ActionRequest` it does emit still passes through the same policy engine and dispatcher as a directly-invoked capability, so a planner bug cannot itself authorize an action.
- `visionai.recognition.gesture.TemporalGestureRecognizer` / `GestureCaptureLoop`: the "recognition services" pipeline stage (see the diagram above) for gestures. The recognizer takes one raw, already-classified single-frame candidate at a time (`gesture_id`, `hand`, `confidence` -- not camera frames or landmarks) and only returns a `GestureVote` once the same gesture/hand has held for `min_hold_ms` at or above `min_confidence`; a gesture/hand change, a low-confidence frame, or `gesture_id=None` (nothing recognized this frame) resets the in-progress hold streak instead of voting on noise. A per-gesture cooldown (`cooldown_ms`) blocks an immediate re-vote of the same gesture once one fires, so a held pose does not fire every frame. `GestureCaptureLoop.capture_once()` wires exactly one `LandmarkAdapter.read_candidate()` call to that temporal vote and then to `InputAdapter.publish_gesture_observation()`. Deliberately not thread-safe: like `TextCommandPlanner` and `ConfirmationService`, it is meant to be driven from one sequential call site (a single camera-processing loop), not shared across threads. `GestureListeningLoop` drives `capture_once()` continuously until a `CancellationToken` is cancelled, mirroring `WakeWordListeningLoop`'s cancellable-consumption shape -- but unlike that loop's injected `AsyncIterable[str]` source, a real (or fake/static) `LandmarkAdapter` is pulled on demand and has no natural "stream exhausted" end, so `cancellation` is a required constructor argument here, not optional, to rule out an uncancellable infinite loop by construction. An optional `stop_gesture_id` field cancels the token itself once a confirmed gesture matches it; `visionai --gesture-listen` sets this to `"open_palm"` so the loop can stop itself with no `Ctrl+C` needed.
- `visionai.orchestration.InputAdapter` / `PushToTalkRunner`: the first input-adapter slice for Phase 3/5 wiring. `InputAdapter` publishes already-recognized voice transcripts as validated `TranscriptEvent`s, can invoke one injected STT provider and publish only its final transcript text, publishes already policy-approved gestures as validated `GestureEvent`s onto the runtime input bus, and can feed one raw single-frame gesture candidate through an injected `TemporalGestureRecognizer` via `publish_gesture_observation()` -- most calls return `None` (building a hold streak, rejected, or in cooldown), and only a confirmed `GestureVote` reaches the bus. `PushToTalkRunner` adds the smallest push-to-talk control boundary around that STT hook: `press()` arms capture, duplicate presses are ignored, and `release()` publishes exactly one final transcript if a capture was armed. It does not capture microphone/camera data, retain raw audio, or classify gestures; those hardware/recognition pieces still belong to later phases. `EventOrchestrator.process_event()` now also handles `GestureEvent`s: a fixed `_GESTURE_COMMANDS` map turns five of the six recognized gestures into a synthesized `TranscriptEvent`, which is then planned and dispatched through the exact same `TextCommandPlanner`/policy/dispatcher path as a typed or voice command -- gesture recognition itself still grants no authority. `closed_fist` is deliberately excluded from this map; `visionai --gesture-listen` instead uses it to start real voice capture (see below), and any other unmapped `gesture_id` would publish nothing.
- `visionai.orchestration.wake_word.WakeWordGate` / `WakeWordVoiceRunner` / `WakeWordListeningLoop`: a second, independent voice-activation boundary alongside `PushToTalkRunner`, over the same `InputAdapter.publish_voice_capture()` path. `WakeWordGate` is pure text logic -- no audio, no I/O -- that matches a configured wake word (default `"visionai"`, sourced from `UserSettingsStore.effective_wake_word()`; may be a multi-word phrase such as `"hey visionai"`) as a case-insensitive whole-word prefix of an already-transcribed utterance and returns the remainder with the wake word stripped, or `None` if the wake word is absent or nothing follows it (an activation with no command is not useful work to publish). `WakeWordVoiceRunner.observe()` feeds it one already-transcribed utterance at a time and only calls `publish_voice_capture()` on a match -- the same "most calls return `None`" shape `publish_gesture_observation()` uses for noisy input. `WakeWordListeningLoop` consumes an injected async source of final transcript strings until exhaustion or `CancellationToken` cancellation, counting only accepted commands. `visionai --wake-word-listen` now wires this to a real source (`app._continuous_transcripts()`, real `MicrophoneCapture` + the default `faster-whisper` transcriber), so real continuous microphone capture and STT are covered -- hotword spotting (detecting the wake word from a live audio stream directly, rather than transcribing fixed chunks and matching text) and raw-audio retention remain out of scope. Not yet wired into `MainWindow`.
- `visionai.orchestration.microphone_capture.MicrophonePushToTalk`: the real Phase 3 capture wiring, mirroring `PushToTalkRunner`'s press/release contract but owning a real `MicrophoneCapture` so recording genuinely starts on `press()` and stops on `release()`, instead of assuming capture already happened elsewhere. When no capture is injected, it uses `default_microphone_capture()`, which reads the persisted Settings device index; explicit capture injection remains available for tests and callers with custom streams. `release()` hands the recorded samples to an injected `transcribe` callable and publishes the result through the existing `InputAdapter.publish_voice_capture()` path -- still no bundled STT engine, and raw audio never leaves this call, matching the "no raw audio in events/storage" invariant. Not re-exported from `visionai.orchestration.__init__` for the same reason `microphone` isn't re-exported from `visionai.platform.__init__`.
- `visionai.orchestration.EventOrchestrator`: the "glue, not authority" layer matching Section 7's pipeline. Consumes `TranscriptEvent`s from a bounded input `EventBus`, plans them via `TextCommandPlanner`, drives the real `StateMachine` through its existing (unmodified for the base path) transition graph -- a text command is framed as an instant, already-final transcript, so it walks IDLE -> LISTENING -> TRANSCRIBING -> INTERPRETING one step at a time rather than needing a new IDLE -> INTERPRETING edge -- dispatches any executable step, and publishes `Intent`/`ActionPlan`/`ActionResult`/`ErrorEvent` to an output `EventBus` for UI/audit consumers. Domain errors (`VisionAIError`) are caught specifically, published as an `ErrorEvent`, and the state machine is always returned to IDLE in a `finally` block regardless of outcome. A request needing both permission and confirmation is gated in that order (matching `PolicyEngine.evaluate()`'s own check order): a `requires_permission` decision parks the request in `AWAITING_PERMISSION` and publishes a `PermissionRequest`; `grant_permission()` writes the grant to the shared `JsonPermissionStore`, re-evaluates the *same* request against a freshly built `PolicyContext`, and only then either raises a `ConfirmationRequest` (`AWAITING_CONFIRMATION`) or executes -- so a grant can never itself authorize an action that still needs confirmation. `cancel_pending_permission()`/`cancel_pending_confirmation()` discard without side effects, and a new command supersedes and discards *both* kinds of pending prompt.
- `visionai.ui.main_window.MainWindow`: the Phase 2 slice -- a minimal PySide6 window (command input, run button, Stop button, Diagnostics button, Settings button, a Gesture Control toggle button, Ask AI and Suggest Command buttons, result display, audit history, tray icon, a confirmation prompt, and a permission-grant prompt), not the full main window Section 14 describes. Adds no planning or execution logic of its own: every typed command becomes a `TranscriptEvent` handed to the same `EventOrchestrator` the CLI and tests use, and command/confirmation/permission execution all run in a Qt worker thread so the GUI event loop stays responsive. If the orchestrator emits a `ConfirmationRequest`, the window shows a `QMessageBox` and then either calls `EventOrchestrator.confirm(confirmation.id)` or cancels the pending confirmation; if it emits a `PermissionRequest`, the window shows a separate `QMessageBox` ("Grant permission") and then either calls `EventOrchestrator.grant_permission(permission.id)` (which itself may still raise a further confirmation prompt) or `cancel_pending_permission()`. The UI never marks anything confirmed or granted by itself -- it only relays the user's yes/no answer back through the same orchestrator calls the CLI could make. The Stop button is never disabled by the Run flow; while a worker is active, it calls `OperationController.cancel_active_operation()` directly so cancellation is not queued behind the serialized dispatcher. The Diagnostics button opens a read-only `QMessageBox` showing runtime/library state (version, Python, PySide6, registered capability count, tray availability, current state, and disconnected voice/camera status), with no path into policy or dispatch. The Settings button opens `_SettingsDialog`, a small `QDialog` with fixed-choice log-level and microphone-device combos plus a validated wake-word field; device enumeration is lazy and failure falls back to the default microphone. Accepted choices persist through `UserSettingsStore`, while `log_dir`/`data_dir` remain environment-only and are not editable from this dialog. The window also exposes `maybe_show_onboarding()`, called explicitly by `main()` (not from `__init__`, so headless tests that construct a `MainWindow` never hit an unexpected modal): it shows a one-time welcome `QMessageBox` summarizing the safety model, gated on `UserSettingsStore.has_seen_onboarding()`. Tested headless via `pytest-qt` with Qt's offscreen platform plugin (`tests/conftest.py` sets `QT_QPA_PLATFORM=offscreen` automatically, so this works in CI with no real display), and the settings/onboarding dialogs were additionally live-verified on the real Windows desktop with a `QTimer`-scheduled modal dismissal (the same technique used for `system.clear_history`'s live check). Keyboard navigation is explicitly verified: initial focus lands on the command input, Tab/Shift+Tab cycle through every interactive control (Run, Stop, Diagnostics, Settings, result, history) in both directions with no trap, and every control has an accessible name; the "Result"/"History" labels are associated with their widgets via `QLabel.setBuddy()`, matching the existing "Command" label pattern. The Gesture Control button closes Phase 5's remaining desktop gap: clicking it builds a real `WebcamLandmarkAdapter`/`TemporalGestureRecognizer` (via the injectable module-level `_build_landmark_adapter()`/`_build_gesture_cancellation_token()`, mirroring `app.py`'s `_build_*` DI pattern) and runs `_GestureListenWorker` on its own `QThread`, driving `GestureListeningLoop` -- the same class and the same `EventOrchestrator`/policy/dispatcher path `visionai --gesture-listen` uses, so a confirmed gesture carries no extra authority here either. The button's label live-updates with a running confirmed-gesture count, doubles as the Stop control (clicking again cancels the loop's `CancellationToken` the same way `--gesture-listen` handles `Ctrl+C`), and the loop still stops itself on a confirmed `open_palm` (`stop_gesture_id`). Runs independently of the text-command worker rather than sharing its `_worker_thread` bookkeeping -- concurrent dispatch from Run and Gesture Control is already safe (see the `StateMachine`/rate-limiter thread-safety fixes above), so gating one behind the other would only add unneeded coupling. If building the real adapter fails (no camera, `vision` extra not installed), the error is caught and shown in the result pane rather than crashing the window. `closed_fist` starts real push-to-talk voice capture the same way `--gesture-listen` does (via the injectable `_build_microphone_capture()`/`_build_transcriber()` factories), and `open_palm` sends it -- giving each `_GestureListenWorker` session its own `MicrophonePushToTalk`. Since this worker dispatches gestures via a direct `orchestrator.process_event()` call rather than the shared input bus (see `_run_session()` below), the sent voice transcript is dispatched the same direct way rather than through `MicrophonePushToTalk.release()`'s own bus-publish path, so its result is visible immediately instead of only at session end. A microphone-capture failure is caught narrowly (`ImportError`/`OSError`/`RuntimeError`/`ValueError`) and reported in the result pane rather than crashing the session; a still-open voice capture is also sent (not discarded) if the session ends some other way first. Ask AI and Suggest Command bring Phase 6's CLI-only `--ask`/`--suggest` surfaces into the desktop window, reusing the exact same primitives (`intelligence._build_llm_provider()`-equivalent factory duplicated in this module the same way `_build_landmark_adapter()` is, `LLMQuery`/`LLMReply`, `suggest_command()`, `runtime.planner.plan()`, `runtime.dispatcher.dispatch()`) with no new authority decisions. Each opens `_TextPromptDialog` (a single free-text field, mirroring `_SettingsDialog`'s `QFormLayout`/`QDialogButtonBox` shape) and runs the request on its own worker thread (`_AskWorker`/`_SuggestWorker`, mirroring `_RuntimeWorker`'s off-GUI-thread pattern so a network call cannot freeze the window). Ask AI only ever shows the reply -- it never writes an audit entry, matching how `--ask` never touches the dispatcher. Suggest Command shows the real proposed action (`"Proposed: <TextCommandPlanner summary>"`) and then asks a genuine `QMessageBox` yes/no question (`_ask_execute_confirmation()`, mirroring `_ask_confirmation()`'s exact shape) before a *second*, separate `_SuggestWorker` instance actually dispatches -- the same "always a fresh worker for the next phase, never one paused mid-run" pattern `_handle_confirmation()` already uses for orchestrator confirmations, so the human answer is never anything the LLM's own reply could have produced. The system tray icon (Section 6's UI component order: main window, tray, ...) has Show/Quit actions and click-to-toggle visibility; closing the window minimizes to tray instead of quitting when a tray is actually available (`QSystemTrayIcon.isSystemTrayAvailable()`), falling back to a normal close otherwise so the window can never become unreachable. Live-verified on the real Windows desktop (tray available, icon visible, close-to-tray works) in addition to the headless test suite, since `isSystemTrayAvailable()` is always `False` under the offscreen platform used for CI.
- `visionai.runtime`: assembles the registry, policy engine, rate limiter, audit sink, dispatcher, operation controller, text planner, input adapter, event buses, state machine, orchestrator, confirmation service, lock-state adapter, and JSON permission store into a single `Runtime` shared by the CLI and the UI. Also builds one `policy_context_factory` shared by the orchestrator and the CLI's direct-dispatch calls, which checks the real `WindowsLockStateAdapter` and `JsonPermissionStore` fresh on every dispatch -- before this, `app.py` and the orchestrator each independently constructed a bare default `PolicyContext()`, so locked-screen mutation blocking and stored permission grants, while implemented and unit-tested in isolation, never actually engaged in the real running application.
- `visionai.app`: console entry point (`visionai` script) that dispatches one capability through the full policy + dispatcher path, plans and dispatches one typed text command via `--text`, runs one already-transcribed wake-word command via `--wake-word-text`, asks the configured LLM provider one question via `--ask` (also runs before `build_runtime()`, like `--list-microphones`, and never dispatches anything -- see `visionai.intelligence` above), asks the LLM to propose a command for free text via `--suggest` (runs *after* `build_runtime()`, unlike `--ask`, since it needs the real registry-backed planner to compute an accurate summary; dispatches only after an explicit human "y"/"yes" answer to a genuine confirmation question -- see `visionai.intelligence.planner.suggest_command()` above), stores or removes the Anthropic API key in the OS keychain via `--set-api-key`/`--delete-api-key` (also run before `build_runtime()`; see `visionai.config.secrets` above), lists real microphone input devices via `--list-microphones` without building the runtime or recording audio, captures up to N real webcam frames via `--gesture-frames N` and reports the first confirmed gesture from `GestureCaptureLoop`, continuously watches for gestures via `--gesture-listen` until `Ctrl+C`, or continuously listens for the wake word over the real microphone via `--wake-word-listen` until `Ctrl+C`. Wake-word text is routed through `WakeWordVoiceRunner` and the real orchestrator before dispatch; dispatch paths use `runtime.policy_context_factory()`. `--gesture-frames`/`--gesture-listen` both build a real `WebcamLandmarkAdapter` and `TemporalGestureRecognizer` (injectable via `_build_landmark_adapter()`/the recognizer parameter, matching `--wake-word-text`'s testability); `--gesture-frames` only publishes to the input bus if a vote confirms, while `--gesture-listen` also drives the real `EventOrchestrator` on a worker thread so a mapped gesture (see `EventOrchestrator.process_event()` above) actually dispatches its capability, and stops itself when the confirmed gesture is `"open_palm"` (`GestureListeningLoop.stop_gesture_id`). `--gesture-listen` also uses `GestureListeningLoop.on_confirmed` to start a real `MicrophonePushToTalk` on `closed_fist` and release it (sending the transcript through the normal dispatch path) on `open_palm`, both built via the same injectable `_build_microphone_capture()`/`_build_transcriber()` factories `--wake-word-listen` uses; a capture failure is caught narrowly and reported rather than crashing the loop. `--wake-word-listen` drives `WakeWordListeningLoop` on its own worker thread with a real, repeatedly record/transcribe `_continuous_transcripts()` source (fixed `_WAKE_WORD_LISTEN_CHUNK_SECONDS` chunks, no VAD or streaming STT); both `--gesture-listen` and `--wake-word-listen` print any dispatched `ActionResult`'s message once their session ends, so a real action's outcome (e.g. `Opening notepad.`) is directly visible rather than only an invisible confirmed/accepted count.
- `visionai.ui.main_window` (`visionai-ui` script): launches the desktop window against a freshly built `Runtime`.

## Migration Rule

The old prototype remains in `../jarvis` and is not part of the trusted VisionAI runtime. Features should migrate only after their contracts, policy checks, tests, and documentation exist in this package. See `docs/MIGRATION_QUARANTINE.md`.
