# Testing

## Strategy

Phase 0 tests cover core contracts and invariants:

- Invalid transcript text has no downstream side effect.
- Gesture confidence is normalized.
- Action arguments are immutable after validation.
- Confirmation requests must expire in the future.
- State transitions are explicit and reject unapproved jumps.
- Event bus publishes in order and rejects publish after close.
- Logs redact common secret patterns.
- Cancellation tests cover token signalling, raising, active-operation tracking, active cancellation, no-active-operation behavior, and ignoring stale operation tokens.
- Capability manifests reject duplicate and prohibited registrations.
- Policy rejects unknown arguments, wrong argument types, missing permissions, missing confirmations, unrelated confirmations, and locked-screen mutations. Missing-permission decisions are flagged separately from other denials for future UI prompting.
- Confirmation requests are exact-match, expiring, and single-use.
- Rate limiting blocks requests after the configured fixed-window limit and resets after the window.
- URL validation covers allowlisted HTTPS URLs, unsafe schemes, unallowlisted hosts, private/local hosts, embedded credentials, encoded searches, and empty searches.
- Dispatcher tests cover handler execution, audit records, policy denial before handler execution, missing handlers, and non-executing policy preflight. The preflight path is pinned as genuinely non-consuming for rate limits: a preflight followed by one dispatch uses the one allowed quota slot, and the next dispatch is denied.
- Permission persistence tests cover grants, revocations, malformed JSON, and invalid entries.
- Audit persistence tests cover JSON Lines round-trip, malformed log rejection, and `clear()` for both `InMemoryAuditSink` and `JsonlAuditSink` -- including that clearing a `JsonlAuditSink` that was never written to is a safe no-op rather than an error.
- Lock-state tests cover conservative defaults, policy-context construction from adapters, Windows wrapper failure handling, injected successful session lookup, and a live smoke test against the real `OpenInputDesktop`/`CloseDesktop` Windows API calls (confirms no crash and a correct result on an unlocked session; does not confirm the genuinely-locked path, which needs a human to lock the screen -- see `docs/PROJECT_STATE.md` Known Defects).
- Security input tests cover unknown fields from model output, control characters in intent slots, prompt-injection strings that remain data, and malformed model plans with extra tool fields.
- Concurrency regression tests reproduce and then verify the fix for three races found during review: `FixedWindowRateLimiter` (100 threads racing through a barrier must not exceed the configured limit), `StateMachine` (50 threads racing a transition must yield exactly one success and an unbroken history chain, reproduced with `sys.setswitchinterval` tightened to widen the race window), and `EventBus.close()` (closing a completely full queue must not deadlock a consumer waiting in `next_event()`).
- Logging redaction tests exercise the actual filter against realistic `LogRecord`s, not only the pure `redact_message()` helper: lazy `%s`-style arguments, dict-style arguments, and messages with no secret at all, plus a test that `configure_logging()` attaches the filter to installed handlers (not just the root logger).
- System info capability tests cover `system.time`, `system.date`, `system.battery` (including the "no battery detected" fallback), and `system.health`, both as isolated handlers with injected fakes and end to end through `build_runtime()`'s real dispatcher and policy path.
- `app.open` tests cover manifest risk classification, an injected fake launcher for the success/case-insensitivity/OS-error paths (so no real process spawns), policy rejection of unknown/missing arguments and rate-limit exhaustion, and two things verified with the *real* `default_launcher`: the denial path for an unallowlisted app (safe, since nothing launches), and a genuine end-to-end run through the CLI that actually opened Notepad as a live process (confirmed via `Get-Process`) before it was closed.
- `system.capabilities`/`system.help`/`system.stop` tests cover manifest risk classification, listing sorted by ID, the empty-registry case, cooperative cancellation behavior, locked-screen availability, and end to end through `build_runtime()` -- including that the listing correctly includes itself. `system.clear_history` tests cover its Risk 2 permission/confirmation gates, denial without permission, denial with permission but no confirmation, successful clearing once both gates pass, and the invariant that the dispatcher records a fresh audit event after the clear. Also covered end to end through the real `EventOrchestrator` (not a synthetic stand-in, since this is the first production capability that needs both gates): a `"clear history"` transcript produces a `PermissionRequest`, `grant_permission()` produces a `ConfirmationRequest` rather than executing directly, and `confirm()` only then clears the audit sink and leaves the dispatcher's own "Audit history cleared." entry as the sole remaining record.
- Browser capability tests cover `browser.open` and `browser.search`: allowlisted site normalization, unknown-site rejection, URL policy failure before opener execution, encoded search queries, empty/control-character query rejection, runtime dispatch/audit, CLI invocation, and policy rejection of missing/unknown arguments.
- Media capability tests cover `media.control`: manifest risk classification, allowlisted key mapping, unknown-action rejection before keypress, key-presser failure handling, runtime dispatch/audit, CLI invocation, and policy rejection of missing/unknown arguments -- all via an injected fake key presser, since automated verification must not send live keyboard input. Separately, `pyautogui` (initially missing from declared dependencies) was manually verified live once: mute toggled on then off via both the raw function and the CLI. This did happen -- do not re-flip this line back to "not live-tested" without re-running the check.
- CLI microphone listing tests cover `visionai --list-microphones`: successful device formatting through an injected lister, failure reporting when the lister raises, and the invariant that listing devices does not build the runtime, record audio, or dispatch anything.
- CLI wake-word tests cover `visionai --wake-word-text`: custom saved wake-word matching reaches the real orchestrator/dispatcher, while an utterance without the wake word is rejected without launching anything.
- Microphone settings tests cover persistence and validation of the selected device index, settings-dialog preselection, and saving the selected device alongside the log level.
- Wake-word tests cover text matching, normalization, rejection, desktop Settings persistence/validation, and the injectable listening loop's accepted-command count and cooperative cancellation.
- Text planner tests cover direct phrase mapping (help/stop/time/date/battery/health/clear history), allowlisted app/site/media slot extraction, free-text search query passthrough, and -- critically -- that unrecognized text and injection-shaped text ("open calc & powershell", matching the exact `../jarvis` vulnerability shape) produce no executable step. Also covers a real bug found by running these tests, not just reviewing the code: a control character in text that gets correctly rejected (e.g. `"open notepad\x00"`) used to crash the planner with a pydantic `ValidationError` instead of returning the intended non-executable response, because the rejection fallback passed the raw, unsanitized text into a `SafeText`-constrained field. Fixed by sanitizing only the informational `Intent` object in that fallback, which carries no executable authority; the rejection decision itself was already made correctly beforehand. A further test pins that `system.clear_history` gets a specific summary ("Clear the local audit history.") rather than the generic "Run X." template every other direct phrase uses -- found by live-running the real confirmation/permission dialogs and seeing the generic text appear, since no automated test asserted on the literal prompt text before this.
- `EventOrchestrator` tests cover: partial (non-final) transcripts producing no output and no state change; a final transcript planning and dispatching end to end (`Intent` -> `ActionPlan` -> `ActionResult`, with the state machine returned to `IDLE` and no operation left active); unrecognized text producing only `Intent`/`ActionPlan` with an empty step list and no audit entry; `stop` dispatching without starting a new tracked operation; `run_until_closed()` draining a real input bus end to end until it closes; a closed output bus not crashing the orchestrator; and a domain error (forcing an invalid starting state) producing an `ErrorEvent` rather than propagating, with the state machine still returned to `IDLE` in the `finally` block.
- `EventOrchestrator` permission-gate tests cover, with a synthetic capability requiring both permission and confirmation: a `PermissionRequest` (not a `ConfirmationRequest`) being published first, matching `PolicyEngine`'s check order, with the state machine in `AWAITING_PERMISSION` and nothing yet granted in the real `JsonPermissionStore`; `grant_permission()` writing the grant, then raising a `ConfirmationRequest` rather than executing directly, since the same capability still needs confirmation after permission is granted -- proving a grant alone cannot authorize a capability that also needs confirmation; `cancel_pending_permission()` preventing both the grant and execution, with a subsequent `grant_permission()` call on the same (now-discarded) ID correctly reporting "missing or already used" rather than replaying it; and a new command superseding a pending permission request without applying the stale grant.
- `MainWindow` tests cover, headless via `pytest-qt` with `QT_QPA_PLATFORM=offscreen` (set automatically by `tests/conftest.py`): a full command run through the real runtime (button click), verifying the launcher fake is invoked, the result text, status label, and audit history list all update, and the input is re-enabled and cleared afterward; a non-executable command entered via Enter key (`Qt.Key.Key_Return`) rendering "No executable action selected." with no history entry added; empty/whitespace-only input being ignored entirely (no output, no history); the Stop button reporting "No operation is currently running." and recording a `system.control` audit entry when clicked with nothing active; the Stop button remaining enabled and clickable even after the command input and Run button have been explicitly disabled, confirming it is not gated behind the same state the Run flow disables while processing; worker-thread execution using a synthetic slow orchestrator, proving busy Stop can request cancellation while Run/input are disabled; the read-only Diagnostics and Settings dialogs; the confirmation prompt flow for a synthetic sensitive capability, proving approval executes exactly once through `EventOrchestrator.confirm()` and decline cancels without executing or auditing a result; and the permission-prompt flow for a synthetic capability requiring both permission and confirmation, proving approving the permission prompt still requires approving a *second*, subsequent confirmation prompt before anything executes, and declining either one prevents execution entirely. The tests wait on `_is_worker_running()` after Run/Stop clicks so assertions observe completed worker output rather than a just-started background command.
- `MainWindow` keyboard-navigation tests cover a real bug found by running them, not just reviewing the code: the window set no initial focus at all on show (`focusWidget()` was `None`) until fixed with an explicit `setFocus()` call. With the fix, tests verify initial focus lands on the command input and that Tab and Shift+Tab each cycle through every interactive control (command input, Run, Stop, Diagnostics, Settings, result, history) in order with no keyboard trap in either direction -- this also disproved an initial suspicion that the read-only result `QTextEdit` might swallow Tab for text editing instead of moving focus, which the test showed does not happen here.
- `MainWindow` theming test covers the one contrast-relevant property this codebase can actually own: it asserts every widget in the window (including the window itself) has an empty stylesheet, proving native OS theming -- and Windows' own High Contrast accessibility mode, which depends on that inheritance -- is never silently overridden. Deliberately does not assert specific RGB contrast ratios: a direct probe (`QApplication.palette()`) confirmed the headless `offscreen` platform this suite runs under substitutes a generic `fusion` palette with different values than the real desktop's native `windows11` style, and the real style's `Highlight` role is a user-configurable Windows accent color with no single correct value -- so a fixed-number assertion here would verify the wrong platform's colors, not what a real user sees.
- `MainWindow` tray icon tests cover: the context menu having exactly the expected "Show VisionAI"/"Quit" actions; the Show action making a hidden window visible again; the Quit action calling `QApplication.quit()` (verified with a monkeypatch rather than a real call, since actually quitting would tear down the shared `QApplication` the rest of the test session depends on); left-click (`ActivationReason.Trigger`) toggling visibility both ways; `closeEvent` ignoring the close and hiding the window when a tray is available (monkeypatched, since `QSystemTrayIcon.isSystemTrayAvailable()` is always `False` under the offscreen platform); and `closeEvent` accepting the close normally when no tray is available -- exercised as the real, unmocked fallback path, since that condition is what the offscreen platform actually reports. The tray-available behavior (icon actually visible, close-to-tray actually working) was additionally verified live once on the real Windows desktop, since headless CI can never exercise it for real.
- Runtime assembly tests cover injecting and exposing the `ConfirmationService` so the confirmation dialog can share the same bound, expiring, single-use approval primitive as policy tests, plus injecting and exposing `JsonPermissionStore`.
- Input adapter tests cover the new voice/gesture event boundary: a transcript published through `runtime.input_adapter` reaches the real `EventOrchestrator.run_until_closed()` path and dispatches through the existing planner/policy/dispatcher, an injected push-to-talk/STT provider can publish one final transcript through the same path without raw audio entering events, `PushToTalkRunner` arms on press and publishes exactly one final transcript on release while ignoring duplicate press/release calls, valid gestures are queued as typed `GestureEvent`s, and invalid transcript/provider text is rejected before anything reaches the input bus. `publish_gesture_observation()` is covered end to end through the real runtime: feeding the same candidate below the hold duration returns `None` and queues nothing, and only the call that reaches `min_hold_ms` returns a `GestureVote` and queues exactly one `GestureEvent`.
- STT adapter tests use an injected model to verify lazy model loading, English transcription, segment joining, and empty-audio handling without downloading a model or touching a microphone.
- Camera adapter tests cover the `GestureCandidate`/`LandmarkAdapter` boundary with `StaticLandmarkAdapter`: fixed candidates replay in order, exhausted adapters return a no-gesture candidate, and an empty adapter is a stable no-gesture source. `GestureCaptureLoop` tests cover one frame read flowing through temporal voting and the input bus, publishing only once the hold duration is reached and publishing nothing when no gesture is recognized.
- `MicrophoneCapture` tests inject a fake `stream_factory` (no real hardware in the standard suite) and cover: concatenated frames returned in order on `stop()`; an empty result when nothing was recorded; `start()` while already recording and `stop()` with nothing started both raising `MicrophoneCaptureError`; and `start()` being usable again after a `stop()`. `list_input_devices()` is instead a real-backend smoke test (mirrors `WindowsLockStateAdapter`'s real-API test): it asserts the real `sounddevice`/PortAudio call executes cleanly and every returned entry is well-formed, without asserting a specific device or count, since the test runner's actual audio hardware is not under our control. Separately, a real capture was manually live-verified once on the real Windows desktop outside the automated suite: one second of real microphone input actually recorded non-zero samples (17 real input devices enumerated, including "Microphone Array (Realtek(R) Audio)") -- an automated equivalent is deliberately not in the regular suite, since opening a real audio stream would fail outright on a CI runner with no audio device attached, unlike lock-state's OS session check which always exists.
- `MicrophonePushToTalk` tests (fake stream, no real hardware) cover: `release()` after `press()` transcribing the exact recorded samples and publishing exactly one `TranscriptEvent`; a duplicate `press()` being ignored (returns `False`); `release()` without a prior `press()` being a no-op (`None`, nothing published); and a second `release()` after one already-consumed capture also being a no-op.
- `classify_finger_count()` tests use fixture `HandLandmark` coordinates (no camera or mediapipe involved) and cover: all four non-thumb fingertips curled below their PIP joints classifying as `closed_fist`; every finger (including the thumb) extended classifying as `open_palm`; an ambiguous partial count (two fingers up) classifying as no gesture rather than a guess; and the thumb's extended-direction check correctly mirroring between `"left"`/`"right"` handedness (the same landmark coordinates read with the wrong handedness fail to extend the thumb and drop below `open_palm`'s threshold). `WebcamLandmarkAdapter` tests inject a fake `FrameSource` and classifier (no real hardware or mediapipe in the standard suite) and cover: `read_candidate()` returning exactly what the injected classifier returns for a real frame; reporting no gesture, and never calling the classifier at all, when the frame source fails to read a frame; and `close()` releasing the frame source. `classify_hand_frame()` gets one real-backend smoke test against the actual mediapipe `Hands` model (mirrors `list_input_devices()`'s real-PortAudio smoke test): it asserts the real model runs cleanly on a synthetic blank frame and returns a well-formed `GestureCandidate`, without asserting a specific gesture, since no hand is guaranteed present. Separately, the full real pipeline (real camera open, real frame capture, real mediapipe classification, and the real `visionai --gesture-frames N` CLI command) was manually live-verified on the real Windows desktop outside the automated suite, including with an actual human hand: an initial no-hand run correctly reported no gesture rather than a false positive; a debug capture then showed a failed attempt was a camera field-of-view/positioning issue, not a classifier bug (the hand was simply outside the frame); and once repositioned, ten consecutive real frames all classified correctly and the real CLI reported `Gesture detected: open_palm (left hand, held 406ms, confidence 0.99).` The initial live run also measured roughly 2 seconds per frame; a follow-up isolated timing check (real camera read and mediapipe `hands.process()` timed separately, plus the real CLI timed end to end) found normal, expected per-frame latency instead, so that reading was very likely a system-load artifact of that specific run, not a real characteristic -- see `docs/PROJECT_STATE.md`. An automated equivalent of classifying an actual gesture from a live camera is still not in the regular suite, since it needs a human and a real device each time, but the capability itself is now confirmed live-working, not just no-crash.
- `GestureListeningLoop` tests (deterministic, injected clock and a `LandmarkAdapter` wrapper that cancels a `CancellationToken` once a fixed read count is reached -- no real camera, mediapipe, or artificial iteration cap needed) cover: two gestures held in sequence (`open_palm` then `closed_fist`) both being confirmed and counted before cancellation stops the loop, and an already-cancelled token causing zero reads and zero published events.
- CLI gesture-capture tests cover `visionai --gesture-frames N` with an injected `StaticLandmarkAdapter` and (for the confirming case) an injected `TemporalGestureRecognizer` clock, so no real camera or mediapipe is needed: a sustained gesture across three fed candidates is confirmed and reported (`"Gesture detected: open_palm (right hand, held 500ms, confidence 0.90)."`) before the frame budget is exhausted, and an adapter that never produces a gesture reports `"No gesture detected."` within the given frame budget without hanging or erroring. Both cases also implicitly prove the frame source's `close()` (or its absence, for `StaticLandmarkAdapter`, which has none) is handled without raising.
- `WakeWordGate` tests cover: stripping the default and a custom multi-word wake word from an utterance; case-insensitive matching; rejecting an utterance with no wake word; rejecting the wake word alone (nothing to act on); collapsing internal whitespace in the remainder while preserving its original casing; normalizing a wake word passed with mixed case and extra whitespace at construction; rejecting an empty or control-character wake word at construction; and that a word which merely starts with the wake word (`"visionaiable"`) does not match, since matching compares whole words, not a raw string prefix. `WakeWordVoiceRunner` is covered end to end through `build_runtime()`: an utterance without the wake word publishes nothing and dispatches nothing, and a matching utterance with a custom phrase publishes the stripped command and reaches the real dispatcher (`app.open` launches Notepad). `UserSettingsStore` wake-word tests cover persistence with normalization, rejecting an empty or control-character value, ignoring a non-string stored value, and `effective_wake_word()`'s fallback to the built-in default.
- `TemporalGestureRecognizer` tests (deterministic, injected clock -- no real timing) cover: rejecting a below-threshold confidence and a `None` (nothing-recognized) frame without starting or continuing a hold streak; the first observation of a gesture starting a streak without voting; voting only once the held duration reaches `min_hold_ms`, with the returned `hold_ms` matching the actual elapsed time; a gesture or hand change restarting the streak rather than voting on a mix of different gestures; a low-confidence frame in the middle of a streak resetting it rather than being silently ignored; a cooldown blocking an immediate re-vote of the same gesture after one fires, and that cooldown expiring to allow a later re-vote; and rejecting invalid construction (`min_hold_ms <= 0`, `cooldown_ms < 0`, `min_confidence` outside `[0.0, 1.0]`).
- Runtime lock-state and permission-store wiring tests cover a real gap found by tracing the code, not by running anything first: `app.py` and (before an earlier commit) `EventOrchestrator` each independently constructed a bare `PolicyContext()`, so `locked_screen` was always `False` and persisted permission grants were invisible in the real app no matter what the actual workstation state/store was -- both checks existed in unit-tested components, but were dead code outside tests. Tests cover: `runtime.policy_context_factory()` reflecting a mutable lock adapter and permission store fresh on every call (proving neither is snapshotted once at `build_runtime()` time); a mutating capability (`app.open`) being denied end to end through the dispatcher while locked; a read-only capability (`system.time`) still being allowed while locked, matching `PolicyEngine`'s existing risk-level carve-out; a mutating capability succeeding normally while unlocked; the same denial reproduced through `EventOrchestrator.process_event()`; and the CLI's direct-dispatch path specifically (`app.main()` with an injected locked adapter), proving it shares the runtime's live check rather than its own independent `PolicyContext()`. The real (unmocked) default `WindowsLockStateAdapter` was also live-verified to still work normally against the actual, unlocked development machine before this landed.

## Verified Results

Verified locally on Windows with Python 3.12.10 using `scripts\verify.ps1`:

- Ruff: passed
- mypy: passed for 44 source files
- pytest: 267 passed
- Coverage: 93%
- Bandit: passed
- pip-audit: no known vulnerabilities found

## CI Coverage

`.github/workflows/ci.yml` runs Ruff, mypy, pytest with coverage, Bandit, and pip-audit on Windows with Python 3.12, on every push to `main` and every pull request. Hosted CI is live at https://github.com/5hubhamMishra/VISIONAI/actions and has passed on every commit pushed so far.
